### 0.2 不可违反的项目约定

1. **服务端权威。** 所有合法性判断都在服务端引擎里，前端只做提示。客户端的 payload 永远不进入引擎构造函数（参见 `StoneSetup` 的注释）。
2. **引擎边界。** 新逻辑放进 `RoomGame` 实现或 `shared/*` 纯函数；`room.ts` 只管身份、权限、版本号、广播和自动化调度。
3. **隐私投影。** `view(selfSeat)` 只能给这个座位应看到的内容。新增的任何“旁观／公共”视图必须用 `view(null)`，并写测试证明不含手牌、军棋暗子等私密信息。
4. **电脑不作弊、不兜底。** 电脑只能通过与真人相同的 `engine.command()` 行棋；电脑引擎不可用时对应难度显示不可用，**不能用随机走法代替**（见 `docs/board-ai.md`）。自研引擎本身可以在低难度里按固定规则从前几名候选里挑，但测试中必须能注入确定的随机源。
5. **界面文案用简体中文**，与现有语气一致（短句、动词开头、不加感叹号）。
6. **原创美术。** 棋盘、棋子、牌面都用项目内 SVG 绘制，不引入外部图片素材，不使用任何商业游戏的名称、商标、牌面版式。
7. **无数据库、无账号。** 房间仍是内存态；本地战绩只存在浏览器里（`src/resultHistory.ts`）。
8. **减少动态效果。** 新动画必须在 `prefers-reduced-motion` 下退化为静态提示（参照 `useBoardPlayback.ts` 的做法）。
9. **不加新的运行时依赖**，除非该阶段明确允许；需要时在 PR 里说明理由与许可证。

## 阶段 2：棋类悔棋

### 目标
中国象棋、国际象棋、围棋、五子棋支持悔棋。**军棋不做**（暗棋悔棋会泄露信息，且四国多方难以协商）。

### 规则设计
| 场景 | 行为 |
|---|---|
| 手机联机（双人） | A 发起“请求悔棋” → B 收到提示，可“同意”或“拒绝”；A 在 B 回应前可“撤回”。同一时间只能有一个请求。 |
| 平板同屏（双人） | 点“悔棋”弹出确认框，确认后直接执行（两人就在同一块屏幕前，不需要再走请求流程）。 |
| 人机对弈 | 点“悔棋”直接退回到**轮到自己时**的局面（通常退两步：电脑一步、自己一步）；电脑正在思考时按钮禁用，执行悔棋时先取消 `pendingBoardAi`。 |
| 退几步 | 退到发起者最近一次落子**之前**。如果对方在那之后已经走过，就退两步；如果是对方回合（发起者刚走完），就退一步。 |
| 次数限制 | 每局每方最多 3 次成功悔棋（数值放在 `shared/` 常量里）。人机模式不限次数。 |
| 不能悔棋的时机 | 对局未开始或已结束；围棋处于点目阶段（`stage === 'scoring'`）；本局还没有发起者的着法；有未处理的和棋请求。 |
| 悔棋后 | 清除和棋请求、清除选中状态；围棋要回退提子数和同形再现集合；五子棋清除 `winningLine`。 |

### 协议与引擎
1. `GameCommandType` 与 `ClientMessageType` 新增 `chessUndo`、`xiangqiUndo`、`stoneUndo`（沿用现有“游戏前缀 + 动作”的命名）。payload：`{ action: 'request' | 'accept' | 'decline' | 'cancel' | 'direct' }`。`direct` 只允许 `room.ts` 在平板同屏或人机模式下调用，客户端直接发 `direct` 时由房间层拒绝。
2. 视图新增字段：`undoOffer: 0 | 1 | null`、`undoUsed: [number, number]`。
3. 各引擎的实现：
   - **国际象棋**：`chess.js` 有 `undo()`；同时截掉 `this.moves`，重新计算 `board` 和 `lastOffer`。
   - **中国象棋**：按 `moves[i].piece / captured` 反向还原（`boardSearchPosition` 里已有同样的逆推写法，可以抽成 `shared/xiangqi.ts` 的纯函数复用）。还要回退重复局面计数。
   - **围棋**：最稳妥的做法是保存每一步之后的 `{ board, capturedCounts }` 快照栈，悔棋直接弹栈；`positions` 集合同步删除对应的局面键。19 路 × 几百手的内存可以接受。
   - **五子棋**：把 `board[point]` 置空即可。
4. `room.ts`：
   - 人机模式与平板同屏时把客户端的 `request` 改写为 `direct`；
   - 悔棋成功后调用 `invalidateAutomation()`，再 `refreshBoardAi()`，保证电脑重新思考；
   - 悔棋会让步数减少，`useBoardPlayback` 会直接跳到新局面、不播放动画，这正是期望的行为。要确认“上一步”标记和路线轨迹被正确刷新为新的最后一步，或者在没有步数时清空。

### 界面
- 在各棋类的操作区（`XiangqiScreen.vue`、`ChessScreen.vue`、`StoneScreen.vue`）加“悔棋”按钮，位置靠近“认输／和棋”，`src/icons.ts` 目前没有撤销图标（`rotate`、`restore` 的含义不同，不要借用），需要按该文件统一的 24×24、1.65 线宽、圆角端点新增一个 `undo`。
- 对方发来请求时，复用和棋请求的提示样式。
- 按钮旁显示剩余次数，例如“悔棋（剩 2 次）”。

### 测试（新增 `tests/boardUndo.test.ts`）
- 四种棋各自：走 3 步后悔棋，局面、轮次、步数、提子数恢复正确。
- 请求 → 同意 / 拒绝 / 撤回三条路径；重复请求被拒绝。
- 次数用完后被拒绝；人机模式不受限制。
- 围棋：提子后悔棋，被提的子回到棋盘，同形再现集合正确回退（悔棋后再下回原处必须合法）。
- 国际象棋：易位、吃过路兵、升变之后悔棋都能正确还原。
- 房间层：电脑思考中悔棋会取消思考；悔棋后电脑重新行棋。
- 客户端直接发 `direct` 被拒绝。

## 阶段 3：五子棋电脑对手

### 目标
五子棋支持与现有象棋相同的五档人机对弈（入门、简单、普通、困难、挑战），入口与象棋一致。

### 架构
1. `shared/boardAi.ts`：`BoardAiGame` 扩展为 `'chess' | 'xiangqi' | 'gomoku'`。
2. `server/bots/boardAi.ts`：
   - `BoardSearchPosition` 改为可辨识联合：现有 UCI 结构加 `kind: 'uci'`，新增 `{ kind: 'gomoku'; board: StoneBoard; size: number; toMove: StoneSide; history: number[] }`；
   - `BoardAiMove` 增加 `{ point: number }` 分支；
   - `availability('gomoku', …)` 始终可用（纯 TypeScript，无外部文件）。
3. 新建 `server/bots/gomokuAi.ts`（纯搜索逻辑，无 I/O，方便单测）与 `server/bots/gomokuWorker.ts`（`node:worker_threads` 包装）。**搜索必须放在 worker 里跑**，避免挑战档的搜索阻塞 WebSocket 事件循环。支持 `AbortSignal`：房间取消时终止 worker 或发送取消消息。
4. `server/room.ts`：`refreshBoardAi`、`boardDecisionCurrent`、`runBoardAi` 里写死的 `view.game === 'chess' | 'xiangqi'` 改成按 `BoardAiGame` 分派；五子棋电脑走 `stoneMove { point }`。阶段 1 之后可以把“如何从 view 取局面、如何把 move 转成命令”收进一个 `Record<BoardAiGame, Adapter>`。
5. 首页 `HomeScreen.vue:170` 的“人机对弈”按钮条件加入五子棋；`BoardAiControl.vue` 对五子棋显示“执黑（先手）／执白”。

### 搜索算法（推荐，可以调整，但要保证测试通过）
- **候选点**：只考虑已有棋子周围 2 格内的空点；空盘时下天元。
- **必胜／必防优先**（所有档位都做，入门档除外）：自己能成五就下；对方能成五就堵；自己能成活四就下；对方有活四时已无法防守，选能延缓失败的点。
- **棋形评估**：对每个点在四个方向上识别 连五、活四、冲四、活三、眠三、活二、眠二，按权重打分（进攻分 + 防守分 × 系数）。
- **搜索**：带 alpha-beta 剪枝的迭代加深 + 置换表（Zobrist 哈希）+ 按启发分排序候选点；困难、挑战档再加 VCF（连续冲四取胜）搜索。

| 档位 | 候选点上限 | 搜索深度 | VCF | 每手时间上限 | 随机性 |
|---|---:|---:|---|---:|---|
| 入门 | 8 | 1 | 否 | 100 ms | 从前 4 名中按权重随机，且 30% 概率忽略对方的活三 |
| 简单 | 10 | 2 | 否 | 200 ms | 从前 2 名中随机 |
| 普通 | 12 | 4 | 否 | 500 ms | 无 |
| 困难 | 15 | 6 | 深度 8 | 1000 ms | 无 |
| 挑战 | 20 | 迭代加深到时间上限 | 深度 14 | 2000 ms | 无 |

随机源通过参数注入（默认 `Math.random`，测试传入固定种子的生成器）。

### 测试（新增 `tests/gomokuAi.test.ts`）
- 永远不返回已占用或越界的点。
- 能一步成五时必定成五（入门以外的所有档位）。
- 对方活四／冲四时必定去堵（入门以外的所有档位）。
- 普通及以上档位必定堵对方的活三。
- 困难档能在给定的 VCF 局面中找到取胜序列（准备 3 个固定局面）。
- 每档都在时间上限的 1.5 倍内返回（CI 机器宽松一些）。
- `AbortSignal` 触发后 100 ms 内结束。
- 房间流程：手机人机房间完整下完一局（可以把电脑设为挑战档、真人走固定的弱棋，断言电脑获胜）。
- 平板模式电脑执黑时，开局后电脑会先落子。

### 文档
- 更新 `docs/board-ai.md`：五子棋一行，说明“自研搜索，无外部引擎，难度是相对档位”。
- 更新 `docs/gomoku.md` 与 README 的“围棋与五子棋”段落。

## 阶段 4：五子棋禁手规则（可选开关）

### 目标
五子棋准备页可以选择“无禁手（默认）”或“黑方禁手”。黑方禁手指三三、四四、长连禁手，白方无禁手，白方长连也算获胜。

### 实现
1. 准备页选项复用 `stoneSetup` 命令（围棋已用它选路数）：五子棋增加 `{ rule: 'freestyle' | 'renju' }`。
2. `shared/stones.ts` 新增 `renjuForbidden(board, point, size): null | 'double-three' | 'double-four' | 'overline'`。
   - **正确性要点**：判断“三”时必须递归确认这个三能走成**真活四**，而且形成活四的那一点本身不是禁手。这是禁手判定里最容易出错的地方，必须写递归。
   - 同一手同时成五与形成禁手形状时，成五优先（黑方获胜）。
3. `StoneGame.command`：禁手规则下黑方下禁手点时拒绝，提示“禁手：三三”等；**不算判负**，只是不能下（休闲规则，在规则文案里写清楚）。
4. 五子棋电脑在禁手规则下执黑时，候选点要过滤掉禁手点；执白时可以利用禁手（把黑方逼到只剩禁手点）。
5. 前端：黑方回合时可以在禁手点上显示小叉作为提示（可选，默认开启）。
6. 规则页（`GameRules.vue`）、教程（`server/tutorials/stones.ts`）加入禁手说明与 2–3 段教程片段。

### 测试
- 至少准备 15 个禁手判定的固定局面，包括：标准三三、四四（含同一条线上的四四）、长连；假三三（其中一个三因为对应点是禁手而不能成活四）；成五同时有禁手形状。
- 白方长连获胜。
- 无禁手规则下行为与阶段 3 完全一致（回归测试）。

## 阶段 5：新游戏——黑白棋

### 目标
新增 `reversi`（界面名：**黑白棋**），8×8，支持平板同屏、手机联机、五档人机、动画教程、战绩，与五子棋的完整度一致。

### 规则
- 初始中央四子交叉摆放，黑方先行。
- 落子必须至少夹住一条线上的对方棋子，被夹住的全部翻转。
- 无合法落点时**自动停一手**（由引擎记录在棋谱里，显示“黑方无处可下，停一手”），不需要玩家点按钮。
- 双方都无合法落点或棋盘下满时结束，子多者胜，相同为和。
- 支持认输；支持阶段 2 的悔棋（如果阶段 2 已完成）。

### 需要改动的位置（阶段 1 完成后应该只剩这些）
| 层 | 文件 |
|---|---|
| 规则纯函数 | 新建 `shared/reversi.ts`：`legalMoves`、`applyMove`（返回翻转列表）、`score` |
| 协议 | `shared/protocol.ts`：`GameKind` 加 `'reversi'`，新增 `ReversiView`、`ReversiGameFields`、`reversiMove`、`reversiResign` |

## 阶段 6：旁观模式

### 目标
聚会时人数常常多于座位。没有入座的人可以通过邀请链接进入**旁观**，实时观看棋盘或牌桌的公开局面。

### 规则
- 所有游戏都可以旁观；每个房间最多 8 位旁观者。
- 旁观者只收到 `engine.view(null)` 的公开投影：看不到手牌、看不到军棋暗子、看不到斗地主底牌（底牌公开之前）。
- 旁观者不能发送任何游戏命令，也不能准备、补机器人、接替座位；可以发快捷语（可由房主关闭）。
- 座位空出来时，旁观者可以申请入座（复用现有的 `requestSeat` 流程）。
- 军棋：旁观者看到的所有棋子都是“暗”。对局结束公开剩余棋子后，旁观者同样能看到。
- 房间信息里显示“旁观 3 人”。

### 实现要点
1. 先通读 `server/room.ts` 中 `join` / `resume` / `requestSeat` 的处理逻辑，以及 peer 与座位的绑定方式，再决定旁观者是否作为“没有座位的 peer”接入。旁观者也要有重连凭证，但这个凭证不能拿到任何座位权限。
2. 广播时旁观者统一用 `view(null)` 生成快照。**这是隐私的关键点**：为每个游戏写一条测试，断言旁观者快照中不出现任何座位的手牌或暗子身份（可以对 JSON 做深度遍历，确认不含私有字段）。
3. 前端：邀请页增加“旁观”按钮；旁观界面复用平板同屏的公共视图（斗地主、掼蛋用 `TabletScreen` 的公共牌桌；棋类用中立视角，黑方或红方在下），隐藏所有操作按钮，顶部显示“旁观中”。

### 测试
- 7 款游戏各自：旁观者快照不含私密信息。
- 旁观者发送游戏命令被拒绝。
- 第 9 位旁观者被拒绝。
- 旁观者断线重连后仍是旁观者，不会占座。
- 旁观者申请入座，房主同意后变为玩家，此后能收到私密视图。

## 阶段 7：棋类棋钟

### 目标
中国象棋、国际象棋、围棋、五子棋、黑白棋可以在准备页设置对局用时。

### 规则
- 选项：关闭（默认）、快棋 5 分钟 + 每步加 3 秒、标准 10 + 5、慢棋 20 + 10；围棋另有“10 分钟 + 3 次 30 秒读秒”。
- 用时耗尽判负（国际象棋：如果对方子力不足以将死，判和，这是标准规则）。
- 只在 `playing` 阶段、轮到该方时计时；房间因断线暂停（`paused()`）时双方都停表。
- 人机对弈时电脑一方不计时，只计玩家一方（或者整体禁用棋钟，二选一，在 PR 里说明选择）。

### 实现
1. 计时状态放在 `room.ts`（与现有牌类的 `turnTimer` 并列），用服务端单调时钟（`performance.now()`）。快照下发 `remainingMs` 与服务端时间戳，前端只负责倒数显示。
2. 引擎接口新增可选方法 `flag?(seatId: number): GameResult`，由房间在超时时调用，引擎负责写入胜负与原因（例如“黑方超时”）。
3. 悔棋（阶段 2）时不退还时间。
4. 界面：双方头像旁显示剩余时间；最后 10 秒变色，并在 `src/haptics.ts` 支持时轻微振动；平板同屏时时间文字跟随各自的棋子朝向。

### 测试
- 用可注入的假时钟测试：加秒、读秒次数消耗、超时判负、国际象棋超时但对方子力不足时判和、断线暂停不计时、对局结束后停表。

## 阶段 8：中国象棋、国际象棋复盘分析

### 目标
对局结束后可以点“分析本局”，用已经安装的 Stockfish 或皮卡鱼给每一步打分，标出失误，并画出局势曲线。

### 实现
1. 新命令 `boardAnalyze`，只在 `phase === 'finished'` 时可用，每个房间同一时间只能有一个分析任务，任何玩家都能发起。
2. 服务端逐手调用 UCI 引擎（复用 `server/bots/uci.ts`），固定预算：每手 50,000 节点或 150 ms，取先到者。返回 `{ ply, evalCp, mate, bestMove }[]`，分批推送进度。
3. 分析结果只放在内存里，跟随房间；开始下一局时丢弃。可以作为可选字段写进本地战绩（`resultHistory.ts`），但要控制大小。
4. 失误分级（以走子方视角计算评分下降）：≥ 300 分为“大失误”，≥ 150 分为“失误”，≥ 70 分为“欠佳”。阈值写在 `shared/` 常量里，并在界面上注明“引擎参考，非绝对结论”。
5. 界面：在棋谱列表旁加一条评分折线（SVG，不引入图表库），点击某一手可以跳到当时局面，并显示引擎推荐的走法（用 `BoardMoveTrail` 画一条虚线箭头）。
6. 引擎不可用时按钮显示不可用并说明原因，与人机对弈一致。

### 测试
- 用一个假的 `BoardAiPolicy`（或假的 UCI 进程）测试：进度推送、取消、开始新局后丢弃结果、对局未结束时拒绝分析。
- `npm run test:board-ai` 增加一项真实引擎冒烟：分析一盘 20 步的固定棋谱。

## 阶段 9：座位数扩展到 2–8 人

### 目标
为阶段 10 的多人纸牌与聚会游戏铺路。本阶段**不加新游戏**，只让基础设施支持 2–8 个座位。

### 实现
1. `GameDefinition.seatCount` 与 `RoomGame.seatCount` 的类型从 `2 | 3 | 4` 放宽为 `number`，并在目录里加 `minSeats` / `maxSeats`，支持“3–8 人都能开”的游戏。
2. `server/room.ts`：`PHONE_SEATS` 改为按人数生成的函数（围绕桌面均匀分布）；检查所有假设“最多 4 人”的地方（座位数组初始化、托管、补机器人、计时）。
3. `src/tabletSeatLayout.ts`、`TabletSeat.vue`：5–8 人时沿桌边排布，头像缩小，保证 1024×768 平板上不重叠。
4. 准备页：可变人数游戏由房主选择人数（与军棋选择双人或四国的方式一致）。
5. 写一个只用于测试的假游戏（放在 `tests/` 下，不进入目录）跑 8 人房间流程。

### 测试
- 8 人房间的入座、准备、开始、断线暂停、接替。
- 布局测试：5、6、7、8 人在平板和手机尺寸下，头像框两两不相交（参照 `tests/tabletSeatLayout.test.ts` 的写法）。

## 阶段 10：新纸牌与聚会游戏

**每款游戏开工前，先单独提交一份 `docs/<游戏>-design.md` 设计文档**，写清规则版本、术语、边界情况、界面草图和测试清单，经人确认后再实现。下面是推荐的三款以及要点。

### 10.1 跑得快（3 人，一副牌去掉部分牌）
- 复用 `shared/doudizhu.ts` 的牌型识别与比较，把差异做成参数：要不要炸弹、三带几、能不能连对、黑桃 3 先出、有牌能管必须管。
- 先选定一个常见的地方规则作为默认，其余做成准备页选项（最多 3 个开关，不要做成规则编辑器）。
- 机器人：DouZero 不能直接用。先写基于规则的贪心机器人（能管就用最小的牌管、尽快走完长牌型），在文档里写清楚它比斗地主机器人弱。

### 10.2 变色出牌游戏（2–8 人，依赖阶段 9）
- 玩法类别：按颜色或数字跟牌、功能牌（跳过、反转、罚抽、变色）、剩一张时必须“报牌”，否则被罚。
- **必须使用原创名称（例如“变色牌”，最终名称由维护者决定）、原创牌面与配色、原创功能牌图标。** 不要使用任何商业同类游戏的名称、商标、牌面版式或标志性的配色组合。
- 牌组构成、罚抽能否叠加、首张翻出功能牌怎么处理，都要在设计文档里定下来。
- 手机“握牌”交互复用 `HandheldHand.vue`；牌比较多（可能超过 20 张）时要测试扇形手牌的可点选性。
- 机器人：规则贪心即可（优先出功能牌压制下家、留变色牌到最后）。

### 10.3 谁是卧底（4–8 人，依赖阶段 9）
- 很适合本项目已有的“每人只收到自己的私密信息”机制（军棋就是这样做的）。
- 每轮服务端把平民词和卧底词分别私发；描述环节线下口头进行，App 只负责计时和轮次提示；投票在 App 内进行，投票过程不公开，投完一起揭晓。
- 词库放在 `shared/` 下，至少 150 组，人工审核过，不含敏感内容。
- 平板同屏模式不适用（每个人的词必须私密），只做手机模式。

## 阶段 11（可选）：围棋电脑对手

- 推荐使用 KataGo：许可证宽松、有 CPU 版本、支持多种棋盘路数。按 `scripts/board-ai-setup.ts` 的方式固定版本、校验 SHA256、写入 `.board-ai/manifest.json`。CPU 版本使用小网络（b6 或 b10），否则在普通电脑上会很慢。
- 通过 GTP 协议对接（需要新写 `server/bots/gtp.ts`，不能直接复用 UCI）。
- 难度用访问次数控制（例如 1 / 8 / 32 / 128 / 512 visits），同样不声明人类段位。
- 点目阶段的死子判定可以用 KataGo 的 ownership 输出给出“建议死子”，但最终仍由双方确认（保持现有规则流程）。
- 引擎缺失时围棋人机入口显示不可用，不用任何自写走法顶替。
